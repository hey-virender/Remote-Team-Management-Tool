# 👥 Remote Team Management Tool

A collaboration platform for distributed teams — projects, tasks, time tracking, file sharing, notifications, and real-time per-task chat over WebSockets.

**🔗 Live Demo:** [remote-team-management-tool.vercel.app](https://remote-team-management-tool.vercel.app)

---

## 📖 Overview

Remote teams lose context in the gap between tools: tasks live in one place, the discussion about them in another, the files in a third. By the time someone asks "why was this decided?", the answer is in a chat thread nobody can find.

This tool attaches the conversation to the work. **Every task has its own conversation**, created on demand the first time someone opens it — so the discussion, the files, the time logged and the task itself stay in one place.

---

## ✨ Features

### 📋 Projects & Tasks

Full CRUD over projects and their tasks, with:

- Priority levels — `Low` · `Medium` · `High`
- Status — `Pending` · `Completed` · `Expired`
- Due dates and assignment to users
- A dedicated status-toggle endpoint, separate from general updates

### 💬 Real-time task chat

Socket.io powers a conversation per task:

- Conversations are **created lazily** — the first user to open a task creates it
- Participants are added automatically on join
- Message history is loaded and replayed on connect
- Each conversation is its own socket room, so messages only reach that task's participants

### ⏱️ Time tracking

Time logs are recorded against work, with full CRUD, so effort per task and per project is measurable rather than remembered.

### 📎 File sharing

Multipart uploads handled by Multer, with files listed, retrieved and deleted through the API and associated with the work they belong to.

### 🔔 Notifications

Notification records are generated by activity across the system and retrievable per user.

### 🔐 Authentication & security

- JWT authentication with bcrypt-hashed passwords
- A `protect` middleware guarding every route except register and login
- Separate admin middleware for elevated actions
- **Helmet** for security headers
- **express-validator** for input validation at the route boundary
- Centralised error-handling middleware, so failures return consistent shapes

## 🏗️ Architecture

```
┌──────────────────────────────────────────┐
│        React + Vite Frontend             │
│   Context providers: Auth · Task ·       │
│   Notification · Error                   │
└──────────┬───────────────────┬───────────┘
           │ REST (Axios)      │ WebSocket
           ▼                   ▼
┌────────────────────┐  ┌──────────────────┐
│  Express REST API  │  │  Socket.io       │
│  protect → routes  │  │  room per task   │
│  → controllers     │  │  conversation    │
└──────────┬─────────┘  └────────┬─────────┘
           │                     │
           └──────────┬──────────┘
                      ▼
              ┌───────────────┐
              │    MongoDB    │
              └───────────────┘
```

The Socket.io instance is attached to every request as `req.io`, so REST controllers can emit real-time events as a side effect of ordinary CRUD — a task status change can notify watchers without a separate messaging path.

## ⚙️ Getting Started

### Prerequisites

- Node.js 18+
- MongoDB (local or Atlas)

### Backend

```bash
cd backend
npm install
```

Create `.env`:

```env
MONGO_URI=your_mongodb_connection_string
JWT_SECRET=your_jwt_secret
PORT=3000
```

```bash
node server.js
```

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Runs on **http://localhost:5173**.

> **Note:** the CORS origin and the Socket.io origin are currently hardcoded to the deployed Vercel URL in `backend/server.js` and `backend/configs/socket.js`. Change both to `http://localhost:5173` for local development.

## 🧭 Design Decisions & Tradeoffs

**Why a conversation per task rather than per project or per channel?**
Channels drift off-topic and lose the link between discussion and work. Binding a thread to a task means the context is always retrievable from the thing it's about — at the cost of not supporting general team-wide chat.

**Why create conversations lazily?**
Most tasks never get discussed. Creating a conversation document for every task would fill the collection with empty threads, so the first participant to open one creates it.

**Why attach `io` to the request object?**
It lets ordinary REST controllers emit real-time events without importing the socket server directly, which keeps controllers testable and avoids a circular dependency between the HTTP and WebSocket layers.

**Why Context API instead of Redux?**
Four independent concerns — auth, tasks, notifications, errors — with little shared state between them. Redux's boilerplate wasn't earning its keep at this size.

## 🚧 Known Limitations

- **CORS and socket origins are hardcoded** and should move to environment variables.
- **No automated tests.**
- **Uploaded files are stored on the server filesystem**, which doesn't survive redeploys on ephemeral hosting — object storage is the fix.
- **No pagination** on list endpoints.
- **Notifications are read-only** — there's no mark-as-read endpoint yet.
- **Admin middleware exists but isn't applied** to any route.

### Roadmap

- [ ] Move origins and config to environment variables
- [ ] Object storage for uploads
- [ ] Mark-as-read and notification preferences
- [ ] Apply role checks with the existing admin middleware
- [ ] Pagination and filtering
